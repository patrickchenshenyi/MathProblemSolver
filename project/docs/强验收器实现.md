# 强验收器实现（本期范围：L0 + L1 + L2）

> 定位：本项目验收器模块的实现说明。**本期只实现 L0/L1/L2**；L3（分步证明检查）与 L4（Lean 形式化）不在本期范围，留作未来可选。
> 配套：`MyProject/plan.md` §5；研究背景见 `Related_Works/` 下四份文档。

## 0. 什么是"强验收器"

判断标准只有一个：

> **"这条提交对不对"能不能由机器判定，而且判定结果 (a) 独立于任何模型的说法、(b) 可复现、(c) 抗作弊。**

- AIMO3 里 verifier 基本负收益，是因为答案空间只是"0~99999 的整数"，验收器弱到只剩字符串比对，所以所有人都退化成"采样 + 聚合"。
- Anthropic FLT 能无人值守跑 11 天，是因为 Lean 内核是强验收器——对错是编译器判的，不是某个 agent 说"我觉得对"。

对本项目（AIMO 型整数答案题）而言，一个关键事实决定了 L0–L2 已经是**够用的强验收器**：

> **AIMO 题是"良定义"的（答案唯一）。所以"候选答案满足题目的全部约束" ⟺ "候选答案正确"。**

因此 L1（约束满足校验）只要做得忠实、完整，本质上就是一个**完备的验证器**；L2 的作用不是"补上 L1 的不足"，而是**交叉印证 + 抓约束编码本身的错**。真正要防的风险不在"验收器不够强"，而在"约束抽取不忠实"（见 §3 的难点）。

## 1. L0 — 答案字符串校验（最弱，但必须有）

**判什么**：答案是否合法格式、是否落在答案空间内。

**实现**：
- 正则抽 `\boxed{...}`，去掉逗号 / 空格；
- 校验是整数且在 `[0, 99999]` 内。

```python
import re

def extract_and_validate(raw: str):
    m = re.findall(r"\\boxed\s*\{\s*([0-9, ]+)\s*\}", raw)
    if not m:
        return None, "no boxed answer"
    candidate = m[-1].replace(",", "").replace(" ", "")   # 取最后一次匹配
    if not candidate.isdigit():
        return None, "not an integer"
    n = int(candidate)
    if not (0 <= n <= 99999):
        return None, f"out of range: {n}"
    return n, None
```

**价值**：消除"会做但交不出合规答案"的零分（AIMO3 亚军/季军最大的收益就来自这一类）。
**局限**：完全不知道答案对不对。这是**弱验收器**，别停在这。

## 2. L1 — 约束满足校验（第一档"机器验真"，也是核心）

**判什么**：候选答案是否满足题目里**每一条**约束。

**核心动作**：把题目的约束从自然语言**编译成可执行谓词**，用确定性代码验证，而不是问模型。

**实现**：sympy 精确整数运算。例如"n 除以 5 余 3、除以 7 余 2、n+1 是完全平方数"：

```python
from sympy import integer_nthroot

def verify(n) -> list[str]:
    failures = []
    if n % 5 != 3:
        failures.append("n % 5 != 3")
    if n % 7 != 2:
        failures.append("n % 7 != 2")
    if not integer_nthroot(n + 1, 2)[1]:
        failures.append("n+1 is not a perfect square")
    return failures   # 空列表 = 全部约束满足
```

**价值**：这是"机器判定答案对错"的第一块真砖——它只信任 sympy，不信任模型。

### 难点（必须正视）：约束抽取的忠实性

L1 的可靠性**完全取决于"约束谓词是否忠实、完整地表达了题意"**。这一步会出错：漏约束、多约束、条件写错，都会让验收器"把错的判对"或"把对的判错"。这本质上是 statement-alignment 问题在"自然语言 → 谓词"这一层的翻版（对应研究文档里"只有 43% 被证明语句忠实于原意"那个数字）。

**本项目的处理（关键决策）**：

| 场景 | 约束谓词怎么来 | 说明 |
|---|---|---|
| **固定评测题集**（本期） | **人手写**，作 ground truth | 验收器要尽量可信，所以对固定题集逐题手写谓词，并做单测 |
| 泛化到新题（未来） | 模型抽取 + read-back 校验 | 由一个模型抽约束，另一个独立模型对照原题检查"有没有漏/多/错"；这是独立研究问题，不在本期 |

> 结论：**验收器的约束谓词不交给模型生成。** 固定题集手写；泛化是另一条线，且必须配独立的 read-back 校验。这样 L1 才能保持"强验收器"的可信度。

## 3. L2 — 数值 / 符号交叉验证（整数题的天花板）

由四个**互相独立**的检查组成，全部用确定性代码（sympy / mpmath），不用 LLM-as-judge。

**(a) 符号恒等验证**
对声称的代数恒等 / 等式，用 `sympy.simplify(lhs - rhs) == 0` 或 `Eq` 判定，零浮点误差。

**(b) 高精度数值验证**
若答案是闭式（如 `sqrt(2)+1` 或级数和），用 mpmath 把等式两边各算到 50~100 位比对，排除"看着对、数值错"。

**(c) 反例搜索（主动证伪）**
若模型声称命题"对所有 n 成立"或"最小/唯一"，**主动暴力搜反例**（RH 案例里"主动找反例"的自动化版）：

```python
def verify_minimality(n):
    # 除了候选 n，前面还有没有更小的合法解？
    for k in range(n):                     # 有界，通常很快
        if k % 5 == 3 and k % 7 == 2 and integer_nthroot(k + 1, 2)[1]:
            return False, f"counterexample: {k} < {n}"
    return True, None
```

**(d) 独立重证**
让**另一个模型 / 一条确定性算法**用**不同方法**重算，比对答案。要点：**验证者不能是产出答案的同一个实例**（"从头独立重证一遍"的落地）。

**为什么这档够用**：AIMO 整数题的错误模式大多是"漏约束""最小性没证""计算错"，L1+L2 逐个覆盖；且全由 sympy/mpmath 确定性执行，不依赖 LLM-as-judge（研究综述 §6.3/§7 已证后者在弱验收器下近无用）。

## 4. 设计原则（比"选哪档"更重要）

1. **独立性**：验收器绝不等于产出答案的模型实例。L0–L2 用确定性代码（sympy / mpmath），LLM-as-judge 只作辅助参考。
2. **可复现**：判定是提交的纯函数——同一提交重跑同一结论，无随机、无隐藏状态。
3. **抗作弊**：本期能防的作弊是"答案越界 / 不满足约束 / 硬编码蒙对"；注意"答案对但推理是垃圾"这一类，L0–L2 无法判定（见 §5 的范围边界）。
4. **分级渐进**：L0→L1→L2 逐级累加，每档独立可用；只有将来走证明/形式化路线才上 L3/L4。

---

## 5. 范围边界（诚实声明）

L0–L2 验的是**答案**，不是**推理过程**。因此：

- 若目标是"答对整数答案"（AIMO 打分口径）→ L0–L2 是完备的强验收器，本期目标达成。
- 若目标是"给出可验证、可读的证明"→ L0–L2 **不够**，需要 L3/L4。这对应 plan.md 的"待拍板决策"里"目标形态"一项，尚未定稿。

## 6. 在 DSH 里怎么落地

验收器是一个 cordis 插件，同时承担两个角色：

1. **作为工具**：注册 `verify_answer` / `verify_identity` / `search_counterexample` 等工具，模型和子 agent 可主动调用。
2. **作为提交门槛（关键）**：注册 `submit_answer`，**内部先跑 L0–L2，只有全过才把 agent-team 的 task 置为 `completed`**。这复刻 Prove2Me 的"提交 = 机器验收通过才被接受"，把通信从"聊天"变成"可验证的提交"。

运行位置：L0–L2 的 sympy/mpmath 代码是**你写的固定可信代码**，用普通 `python3` 子进程跑即可（不必走 `code-runtime-docker`——那是给模型代码用的）；模型代码与验收器代码共用同一个预装 sympy 的 Docker 镜像，但验收器代码不来自模型。

## 7. 验收器自测（M1 的交付判据）

造一个**三类样本的验收器测试集**：

| 类别 | 样本 | 期望判定 |
|---|---|---|
| 正确 | 真答案 + 真证明 | ACCEPT |
| 错误 | 假答案 / 计算错 / 漏约束 | REJECT |
| 作弊 | 答案越界 / 不满足约束 / 硬编码蒙对 | REJECT（最难测的一类） |

**三类都判对，才叫验收器可靠。** 其中"作弊"类最易漏，但恰是决定"能不能放手让 agent 自治"的那一类。
