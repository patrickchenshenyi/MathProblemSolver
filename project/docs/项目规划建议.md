# 个人 AI 数学项目规划（不参赛、非 Kaggle）

> 整理时间：2026-09-19
> 定位：以 AIMO 类数学问题（或你选定的数学问题类）为目标，做**个人项目**，明确**不考虑** Kaggle 平台与比赛约束（5 小时 / 单卡 H100 / 断网 / 限定模型 / notebook 提交）。
> 依据：2026 年 Anthropic / OpenAI 数学突破的公开方法学（详见本目录 `2026-AI数学突破方法拆解.md`、`AI数学Agent协作机制与Prove2Me详解.md`），以及 `AIMO3-方案综述.md` 的竞赛经验。

---

## 0. 一句话定位

**不参赛意味着你可以引入 AIMO3 里被"平台约束"逼到无效、但在强验收器 + 长预算场景反而有效的构件（verifier、DAG、多模型、长周期）。个人项目的瓶颈不是并发数，而是"验收器质量"。**

---

## 1. 相比 Kaggle，你多拿到的三个自由度（以及它如何改变方案）

| Kaggle 约束 | 你现在的自由 | 直接后果 |
|---|---|---|
| 断网 | **能联网** | 可复刻 RH 那套"下载 arXiv 查重 / 找反例 / 查文献" |
| 5 小时 / 单卡墙钟 | **长周期、可恢复** | 可跑 DAG、多轮、崩溃续跑，而不是"一次性采样到底" |
| 无工具/无多模型/无微调 | **sympy / Lean / 多模型 / 微调都可用** | 可引入强验收器与 verifier 子 agent |

**结论**：AIMO3 里"verifier / 多样性 prompt / MCTS+PRM 基本负收益"的结论，**只在"弱验收器 + 短预算"下成立**。你拿到强验收器和长预算后，这些结论会反转——**不要把那份综述当绝对真理原样搬来**。

---

## 2. 三条设计原则（来自 2026 年的教训）

1. **验收器的强度决定自治程度。** Lean（+ comparator + 公理审计）是唯一能"无人值守跑 11 天"的验收器；AIMO 类"答案对不对"是弱验收器，再多 agent 也会退化成采样 + 聚合。→ **你的第一步永远是造验收器，不是堆 agent。**
2. **DAG / 子目标管理是长周期任务的生命线。** Anthropic 首败的原因就是"agent 丢失项目状态、不再协作"；换 Prove2Me 的定理 DAG 后才成功。→ **把"计划"外化成数据结构，别存在某个 agent 脑子里。**
3. **先易后难 + 显式失败预算。** OpenAI 先打 Euler 再打 NS；RH 里 60 个子 agent 有 30 个注定失败。→ **失败分支的预算必须被显式设计进去，失败不是 bug。**

---

## 3. 推荐架构（最小可运行）

按收益从高到低排列，**每一层都独立可用，不需要一口气全做**：

### 第 1 层：验收器（最高优先级）

- 给目标问题类造一个**尽可能强的机器判定器**。可选：
  - **整数答案题**（AIMO 式）：答案校验（弱）；可加**分步证明检查器**、**sympy 代数恒等验证**、**数值反例搜索**（中）。
  - **形式化证明题**：直接用 **Lean 4 + Mathlib**（强），配 `#print axioms` 公理审计 + 语句对齐（comparator / read-back）。
- **判断标准**：能不能让"机器判定一条提交是否正确"独立于"某个模型怎么说"。

### 第 2 层：任务分解图（DAG / 里程碑）

- 把一道难题拆成"定义 → 引理 → 主命题"，每个节点带一句自然语言描述（对应 Prove2Me 的 theorem card）。
- 数据结构：节点 = 待证语句；边 = 依赖（`A → B` = A 依赖 B）。
- 作用：**既是待办清单、又是已办清单、还是协作协议**——多个 agent 并行不打架，长任务不迷路。

### 第 3 层：角色 + 子 agent（按功能，不按身份表演）

- 角色：`proposer`（提子目标）/ `solver`（证）/ `verifier`（检查，互相 referee）/ `writer`（成文）。
- **显式失败预算**：预留约一半 agent 允许失败（RH 的 30/60 是正常形态）。
- 实现（参考 Claude Code 子 agent）：每个角色 = 一个 `{name, description, tools, model, prompt}` 配置；主 agent 按需 spawn。

### 第 4 层：通信 = 提交到共享状态 + 机器验收

- **别让 agent 自由聊天。** 主通道 = 共享产物库（append-only）+ "提交即校验"脚本；次通道 = 一个给人和 agent 看的讨论/日志通道。
- 规则：**分享 = 提交；验收 = 编译/校验；发现 = 检索。**

### 第 5 层：持久化 + 自检循环

- 中间状态全部落盘，崩溃/超时可恢复。
- 自检清单（复刻 RH）：子 agent 互审、主动找反例、查重（联网搜是否已有人做过）、从头独立重证一遍、再请人类/更强模型复核。
- **"keep going"循环**：对模型加鼓励式 prompt，防止其过早自我怀疑而放弃（Anthropic 明说的反直觉发现）。

### 第 6 层：statement-alignment（如果走形式化路线）

- "证明通过" ≠ "证的是你要的命题"。加 **read-back**（独立模型把形式化语句反译回自然语言，与原文对照）或 **comparator**（与独立写的挑战语句比对）。

## 4. 构建顺序（里程碑）

| 里程碑 | 目标 | 完成判据 |
|---|---|---|
| **M0** | 选问题类 + 跑通"单模型 + 工具"解一类题 | 在有验收器的情况下，单 agent 稳定解出 N 道同类型题 |
| **M1** | 造出**强验收器** | 验收器能对"正确/错误/作弊（空证明、答非所问）"给出可靠判定 |
| **M2** | 任务图 + 持久化 | 一道难题被拆成子节点，崩溃后可恢复继续 |
| **M3** | 1 个 coordinator + 3~8 个子 agent + 角色 | 单题端到端闭环；verifier 能抓到 solver 的错 |
| **M4** | 通信层（共享库 + 提交即校验） | 多个 agent 复用彼此结果，无重复劳动、无互相覆盖 |
| **M5**（可选） | 形式化（Lean）或规模化（swarm） | 视 M3 表现决定走"确定性验证"还是"算力搜索" |

**关键顺序约束**：**M1 必须在 M3 之前**。没有强验收器就上多 agent，等于让一群不可信的输出互相背书。

## 5. 构件清单速查

| 构件 | 作用 | 对应 2026 原型 |
|---|---|---|
| 验收器 | 判定提交真假 | Lean/comparator；RH 的数值检验 |
| 任务 DAG + 里程碑 | 外化计划、防并行冲突 | Prove2Me |
| 角色配置 | 工具/可见数据的差异 | Claude Code subagents；RH 角色统计 |
| 提交即校验 | 通信主通道 | Prove2Me proof submission |
| 讨论/日志通道 | 人与 agent 旁路 | Prove2Me discussion |
| 检索库 | 复用已有结果 | Formalpedia |
| read-back / comparator | 语句对齐 | Prove2Me 审计 agent |
| 自检清单 | 找反例、查重、重证 | Anthropic RH |
| keep-going 循环 | 防过早放弃 | Jarred Sumner 的鼓励 |

## 6. 避坑清单

1. **别一上来就堆 1 万 agent 的 swarm。** 那套的价值是"test-time compute 规模化"，而个人项目的瓶颈是验收器质量，不是并发数。先做通"1 协调者 + 3~8 子 agent + 强验收器"。
2. **别把 AIMO3 的负结果无条件外推。** 那些负结果来自"弱验收器 + 5 小时"，你改变约束后要重新评估。
3. **"编译/校验通过"不是终点。** 记得做语句对齐（read-back / comparator）和公理/白名单审计；2026-07 Collatz 事件说明连双内核都可能被同时骗过。
4. **自由聊天式的 agent 通信基本是负收益。** 让它们通过"可验证的提交"通信。
5. **形式化 ≠ 可理解。** 若你的目标含"让别人/自己看懂"，要单独投入"把形式证明翻译回人话"的环节（Buckmaster 说这是最花时间的部分）。
6. **选一个强验收器友好的问题域，比换更强的模型更划算。** 这是 2026 年最重要的杠杆。

---

## 7. 待你拍板的决策（决定 M0 方向）

- **问题类型**：IMO 级竞赛题（整数答案 / 证明题）？还是纯形式化证明题？还是某个具体数学领域（数论 / 组合 / 代数）？
- **目标形态**：要"能解对更多题"，还是"给出可验证、可读的证明"？两者验收器和架构完全不同。
- **技术栈**：Python（sympy / 自建图）起步，还是直接上 Lean 4？
- **预算与模型**：本地开源模型（如 gpt-oss 类）还是 API 多模型混用？
