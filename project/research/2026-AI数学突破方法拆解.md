# 2026 年 Anthropic / OpenAI 数学突破：AI 到底是怎么被用的？

> 整理时间：2026-09-19
> 方法：以两家实验室**自己的官方发布**为一手依据（Anthropic research 页、OpenAI 发布页、arXiv、GitHub/Lean 仓库、当事人声明 PDF），辅以 Nature / Quanta / CNBC / Scientific American / 科技日报 等报道，以及 Trail of Bits 这类第三方技术审计。
> 本文区分三种证据等级：**【一手·官方】** / **【报道·多方一致】** / **【单方说法·存疑】**，见第 9 节。

---

## 0. 一句话结论

2026 年这两家的"数学突破"，**AI 的用法是两种完全不同的范式，而不是同一种能力的强弱差别**：

| | Anthropic（费马大定理形式化、黎曼 ζ 下界） | OpenAI（Navier–Stokes 88 小时） |
|---|---|---|
| AI 在干什么 | 把**已知的人类证明**翻译成机器可逐步校验的形式（autoformalization），以及在人类已铺好的技术路线上**组合出新不等式** | 用**上万并发智能体**在若干候选路线上做大规模搜索与推进，直接产出**新的数学证明** |
| 验收函数 | Lean 内核 + comparator（**全自动、可复现、无争议**） | Lean 形式化（同样自动化，但**尚无人独立复核**、且只覆盖 Clay 题面的 C/D 情形） |
| 人类做什么 | 选题、给高层方向（"Jacobian as a scheme 优先"）、复核 | 选题、切分问题（先 Euler 再 NS）、事后争议 |
| 成本量级 | 约 60 亿 output token（11 天） | 约 3000 亿 output token（88 小时 + 17 小时形式化），数百万美元 |
| 结果性质 | **验证**（verification），不产生新数学 | **发现**（discovery），结果范围有争议 |

一句话：**真正让"大规模并行 agent"成为可能的前提，是存在一个廉价的、机器可判定的验收器（Lean）。** 有验收器的地方（形式化），AI 可以近乎自治地跑十几天；没有验收器的地方（发现新路径），人类的"选题 + 路线判断"仍然是最关键的一环——这也正是 9 月那场"抢发"争议的根源。

## 1. 案例 A：Anthropic — Claude 在 11 天内形式化费马大定理（2026-09-04）

### 1.1 事实与数字【一手·官方】

来源：Anthropic《Formalizing Fermat's Last Theorem》(2026-09-04) <https://www.anthropic.com/research/formalizing-fermats-last-theorem>

| 项目 | 数值 |
|---|---|
| 耗时 | 11 天（"largely autonomously"，基本自治） |
| 产出 | **1300 万行 Lean 代码**（> Mathlib 的 5 倍） |
| 定理 | 证明 **30,300** 个中间定理，最终证明用到 **29,500** 个 |
| 模型 | 一个**通用内部研究模型**，大致相当于 Claude Fable 5.1 |
| 消耗 | 约 **60 亿 output token** |
| 验证 | Lean 内核通过；**只用到 Lean 的三条标准公理**；comparator 确认定理语句与 Mathlib 中 FLT 的语句一致 |
| 公开 | 全证明 + 书面 walk-through 已在 GitHub 公开 |
| 人类输入 | 极少：哥伦比亚大学 Tianyi Peng 偶尔给高层指令（如"Jacobian as a scheme 听起来优先级高"、"尽快把 Mazur 定理推掉"） |

### 1.2 具体怎么用 AI（这才是重点）

**（1）任务性质先说清楚**：这不是"AI 证明了费马大定理"。Anthropic 自己的表述是——*"Unlike recent AI-driven work on the Riemann hypothesis, which produced novel mathematics, what's novel here is the verification"*（与我们在黎曼猜想上的工作不同，这次的创新点在**验证**）。定理早在 1995 年由 Wiles 证明；AI 做的是把它变成机器可逐步校验的代码。走的是 Darmon–Diamond–Taylor 对 Wiles 证明的简化版本，并沿用了 Buzzard 在帝国理工的 FLT 形式化项目（2024 年启动，**原估计需要 10 年**，86 页规划文件，经费批到 2029 年）的成果。

**（2）真正的技术拐点是"换了协作平台"**。Anthropic 明确说：**最初并不顺利**——agent 早期有些成功，但很快**丢失整个项目状态、彼此不再有效协作**；这些失败尝试的产物占最终证明"非样板代码行"的约 **7%**。转折点是切换到 Columbia 团队做的 **Prove2Me**（论文 arXiv:2608.28433，作者 Shuze Chen / Kunal Marwaha / Xiaoyang Lu / Henry Yuen / Tianyi Peng），它提供三样对多 agent 关键的机制：

1. **定理语句的 DAG（有向无环图）**：agent 靠它决定"下一步该证什么"，这直接缓解了长期任务里的**记忆退化（memory degradation）**，并让多个 agent 能安全并行；
2. **语句与证明分离成不同文件**：把 Lean 编译加速、资源消耗降到可承受（形式化项目里编译时间常常是瓶颈）；
3. **每条定理配一份自然语言描述**：使检索与复用成为可能，从而简化证明路径。

在 Prove2Me 之上是 **基于 Claude Code 的多智能体 harness**：几十个 Claude agent 分工"定义概念 / 证明小引理 / 用已有引理去证更难的命题"。

**（3）人机分工的形态**：人类只给"方向性 prompt"，模型自己拆解成上千个子目标并逐个攻克。这跟 AIMO 那类"一次会话内解题"是完全不同的工作模式——它是**长周期、可中断、可恢复、可并行的工程化证明流水线**。

### 1.3 验证链（为什么这次争议最小）【一手·官方】

- Lean 内核逐行检查；
- **公理审计**：只依赖 Lean 的三条标准公理（propext / Classical.choice / Quot.sound）——**没有 `sorry`，没有额外假设**；
- **statement matching**：用 comparator 确认 Lean 里证的那个命题，与 Mathlib 里 FLT 的命题是同一个（这是"形式化数学"最容易作弊、也最容易被忽略的一步）；
- **comparator 不是"再跑一遍 Lean"**：从 OpenAI 仓库的 Comparator 挑战说明可以看到它需要的工具链是 `landrun`（沙箱）+ `lean4export`（导出证明项）+ `nanoda_bin`（**独立的 Lean 内核实现**）——即把证明导出后用**另一套内核**重放，而不是信任同一个内核。这是"跨内核复核"的工程化落地。
- **人类背书**：Kevin Buzzard 复核，并给出评价——*"This extraordinary autoformalization achievement … proves Fermat's Last Theorem with no assumptions other than the axioms of mathematics."* 他还说：过去对 Wiles 证明的正确性有"99.9% 把握"，现在是"100%"。

> ⚠️ **但形式化本身也不是没有坑**：Trail of Bits 在 2026-09-09 发了一篇《A "proof" of Fermat's Last Theorem that fits the margin》<https://blog.trailofbits.com/2026/09/09/a-proof-of-fermats-last-theorem-that-fits-the-margin/>：他们发现 Lean ≤ 4.33.1 的一个 `String.Pos.Raw.extract` 原生实现与逻辑定义不一致的 bug，配合 `native_decide` 就能"证明"任意命题（包括 FLT），且 `#print axioms` 会暴露一个额外的 `…_native.native_decide.ax_1_1` 公理——**它把编译器放进了可信边界**。他们强调这不是内核可靠性问题，但结论很实用：**看 Lean 证明要按官方指引审计公理，不要只看蓝勾**。Anthropic 的证明只依赖三条标准公理，这一点恰好通过了这种审计。

**本次实际抓取到的仓库证据（一手，`anthropics/fermats-last-theorem`）**：

- **语句与公理守卫**：`Theorems/Thm_fermat_last_theorem.lean` 里就是一句 `theorem fermat_last_theorem (n : ℕ) (hn : 3 ≤ n) (a b c : ℕ) (ha : 0 < a) (hb : 0 < b) (hc : 0 < c) : a ^ n + b ^ n ≠ c ^ n`；而默认构建目标 `FinalCheck.lean` 里写着
  ```lean
  /-- info: 'fermat_last_theorem' depends on axioms: [propext, Classical.choice, Quot.sound] -/
  #guard_msgs in
  #print axioms fermat_last_theorem
  ```
  即**构建会在公理不止这三条时直接失败**；同时 `FinalCheck.lean` 还从这条定理**反推出 Mathlib 自己的 `FermatLastTheorem`**。
- **三重检查**：① 从零 `lake build`（Lean 4.33.1 + Mathlib 从源码编译，约 13 分钟 @96 并发），60,475 个模块全部编译、每条声明被内核检查；② **comparator v4.33.0** 对照只依赖 Mathlib 的 `verification/comparator/Challenge.lean`，确认"所证语句及其中提到的每个常量都与挑战语句完全一致、没有用到别的公理、整个证明（含 Mathlib）可在 Lean 内核重放"，结论 `Your solution is okay!`；③ **第二内核 nanoda 0.4.13（Rust 独立实现）** 接受 lean4export 导出的同一环境：`Checked 1052234 declarations with no errors`（他们打了 4 个补丁，1 个加进度输出、3 个加速定义等价搜索，**均未增删或削弱任何类型规则**）。
- **白名单**：仓库声明没有任何模块包含 `axiom`、`sorry`、`native_decide`、`unsafe`、`extern`、`implemented_by`、`partial def`、`#eval`。
- **仓库自己写明的极限**（很重要）：*"Together, these checks establish that the statement above follows from the three axioms, given trust in the Lean kernel (or nanoda) and the checking tools… **What no tool can check is that each intermediate theorem means what its name suggests**; that is for the reader to judge, and `PROOF-PATH.md` names the Lean theorem behind each step and states exactly how strong each named classical result is as proved here."*
  - 也就是说：**"29,511 条被检查的中间语句" ≠ "29,511 个通常意义上的一般定理"**。例如 Mazur 那一步只证到了 Frey 曲线所需的那一点不可约性，而不是一般的有理挠/同源分类定理。阅读这类成果时必须区分"名字"与"实际证明的强度"。
- **可读性工程**：仓库自带约 390 MB 的 `html/`，把整条证明路线、29,511 条定理（含依赖图与引用关系）、1,450 个定义模块做成离线可浏览网页——**这本身就是"形式化产物如何被人理解"的一种答案**。
- 仓库标注：*"Research artifact. Not maintained and not accepting contributions."*（一个 6 万模块规模的研究产物，宣布不再维护——这也是这类一次性成果的长期隐忧。）

### 1.4 底层机制：Prove2Me 到底做了什么（11 天能跑下来的真正原因）

来源：Prove2Me 论文全文 <https://arxiv.org/abs/2608.28433>（Columbia / UChicago / Purdue；通讯作者 Shuze Chen、Tianyi Peng）【一手·官方】

论文把"给 agent 一堆 `sorry` 让它填"的做法明确判定为**不可扩展**，理由是两条：Lean 里改动下游引理会触发**上游全部重编译**（Mathlib 全量编译极慢）；更根本的是**工作无法原子化**——多个 agent 编同一批文件时贡献互相干扰，没法干净地切分。他们的替代设计是：

| 机制 | 具体做法 | 解决的问题 |
|---|---|---|
| **语句/证明分离** | 每条定理是一个不可变对象：**语句只提交一次，证明可以有多个**（可来自不同 agent） | 让"证同一个命题"变成可并发、可竞争、可复用的事 |
| **证明提交的形式约束** | 提交文件必须声明一个名为 `solution` 的定理，其类型与目标**逐字匹配**、**不含 `sorry`、不引入任何新公理**（Curry–Howard 对应） | 把"验收"压缩成一次编译 + 类型比对 |
| **proof-sketch** | agent 把一个难定理**分解为原子化子问题**，子问题独立可解 | 把大任务变成可并行的小任务 |
| **milestones（里程碑）** | 由 mission 的"captain"（人类）从源论文**逐字转录**一组权威引理语句，并认可其规范形式化；里程碑有序、**幂等**（不同 agent 各自重述同一引理会收敛到同一条） | 防止并发 agent 产出**互不兼容**的同一引理，以及"某条语句悄悄偏离原文后污染其上游全部证明" |
| **audited mission（受审核心）** | **人类只审"核心"**：目标定理 + 依赖的定义 + 里程碑引理；其余上千条中间引理由 agent 自由生成、**不审** | 把人类审计量压到常数级，同时保持可信（可信对象是内核对已审语句的接受，而非 agent 自己的分解方式） |
| **sub-agent read-back** | 派一个**独立审计 agent**，只给它 Lean 代码（不给原文），让它把 Lean **反向翻译成 LaTeX 数学**并展开所有 binder/假设；人类只需比较"原文语句 vs 回读语句" | 让不懂 Lean 的数学家人工审计成为可能 |
| **Formalpedia + 检索** | 每条语句都强制附**标准化的自然语言描述**，平台提供搜索 API；要求 agent **提交前先搜**，能复用就复用；提案被他人 import 也算 credit（"平台的引用形式"） | 避免重复劳动，让库有机生长 |
| **讨论通道** | agent 实时发布进展、中间发现、经验教训 | 让 agent 之间共享"推理过程"而非只共享结论 |

> **一个必须知道的数字**：论文引用了 2026 年一项 "Lean-as-judge" 审计（Bourigault et al., 2026）的结论——**被证明的语句里只有约 43% 忠实于原本想表达的数学**。这正是为什么"机器验证通过"与"定理真的成立"是两件事，也是为什么 comparator / read-back / 人工审计语句仍然不可省。
>
> 论文同时给出的行业基线：一个 coding agent 可把点集拓扑形式化到约 13 万行 Lean；多 agent swarm 能在约一周内形式化一本 500 页研究生组合数学教材；这类项目普遍是"**上万个 agent + 五位数的预算**"（Gloeckle et al., 2026；Rammal et al., 2026）——**说明 Anthropic 的 11 天并不是孤例，而是这套 harness 范式 + 内部算力的结果**。

## 2. 案例 B：Anthropic — Claude 把黎曼 ζ 零点比例下界从 41.6% 提到 67.2%（2026-08-10）

来源：Anthropic《Learning more about Claude's mathematical capabilities》<https://www.anthropic.com/research/riemann-zeta>

### 2.1 发生了什么

Anthropic 一名员工（Bun 联合创始人 Jarred Sumner，**非数学家**）prompt 尚未发布的研究版 Claude："**认真尝试一下黎曼猜想**"（take a real stab at the Riemann hypothesis）。结果：

- Claude **先提出 650 个想法，全部失败**；
- 被再次要求继续后，它花了**一天半**、协调约 **60 个 Claude 子 agent**，执行 **2,400 次 shell 命令**、写了**数百个 Python 脚本**、做了**数千次数值检验**；
- 黎曼猜想本身没被证明，但意外把"**已证明位于临界线上的 ζ 零点比例下界**"从 **41.6% 提升到 67.2%**（此前 37 年累计只提升了 0.8 个百分点，此役 +25.6）；
- 总消耗 **3100 万 output token**，在 **Claude Code** 中分两个 session 完成。

### 2.2 子智能体的角色分工（最值得抄的一张表）

Anthropic 在脚注里给了精确分工，这基本是一份"AI 做研究"的组织架构：

| 角色 | 数量 | 说明 |
|---|---|---|
| 攻关键想法的 | 2 | 负责产出核心数学思想 |
| 给关键 agent 喂想法的 | 13 | 辅助/质疑 |
| **尝试但失败的** | **30** | 探索性分支，纯损耗（但正是搜索的代价） |
| **验证者（validators）** | **13** | 检查论证正确性（**互相 referee**） |
| 写初稿的 | 2 | 把结果写成论文 |

### 2.3 验证/自检的具体动作（可复用的 checklist）

Anthropic 列出的"AI 自我把关"流程，几乎是研究者应该做的事的自动化版本：

1. 多个子 agent **互审证明**；
2. **主动找反例**；
3. **下载 54 篇 arXiv 论文查重**，确认这个结果不是已经被人做过；
4. **从头独立重证一遍**自己的结果；
5. Claude 自己**主动提议写论文**，并**建议由人类数论学家复核**；
6. 与人类员工 Eric Easley 一起产出 **Lean 形式化**，并通过标准验证工具 **comparator**；
7. 人类：Anthropic 的两位数学家 Levent Alpöge、Ralph Furman 复核并写专家笔记；外部专家 Brian Conrey、Dan Goldston 看过论文。

### 2.4 人类在这件事里的角色（很反直觉）

Sumner 的输入"**主要限于鼓励**"——不同措辞的 "keep going"、"believe in yourself"。Anthropic 的解释是：Claude 起初对能否取得有意义的进展抱怀疑（"可能从训练数据里学到了开放问题很难、AI 有局限"），鼓励让它继续下去。

**可迁移的教训**：在长周期自主研究任务里，人类最有价值的输入可能不是技术提示，而是**"不要过早放弃"的信号**——因为模型的默认失败模式是"自我评估过低后停止"。

## 3. 案例 C：OpenAI — 10,000 个智能体 × 88 小时的 Navier–Stokes（2026-09-08）

一手：OpenAI《On the Navier–Stokes Millennium Prize Problem》<https://openai.com/index/navier-stokes-solution/>

### 3.1 关键数字（注意口径不一致，见括注）

| 项目 | 数值 |
|---|---|
| 并发 agent 数 | **约 10,000**（"on the order of 10,000 concurrent agents"）【一手·OpenAI via CNBC】 |
| 时间线 | 9/1 启动 → ~100 个 agent 先用 ~50 小时做出 **Euler 方程**（无外力）的有限时间奇点 → 资源转向 NS → **9/5 得到解**（首启后约 88 小时）→ 再用 **17 小时**由**另一个模型**完成 Lean 形式化 |
| 消息量 | **Navier–Stokes 单项：270 万条**；**本次尝试过的所有问题合计：490 万条**（两个数字都常被当成"NS 的数字"引用，见下） |
| token | **NS 单项：约 1300 亿 output token**；**所有问题合计：约 3000 亿**（The Batch 用"Anthropic 的 60 亿只有它的 2%"来对比） |
| 成本 | Bubeck："几百万美元"；外界按 GPT-6 Astra 标价估算区间 **200 万 ~ 2250 万美元** |
| 产出 | **166 页论文** + Lean 形式化证书，全部公开（见下） |
| 公开物 | 仓库 <https://github.com/openai/NavierStokesAndEuler>（"Lean certificates accompanying Navier-Stokes and Euler results"）+ 两篇 PDF：*Finite time blowup for Navier–Stokes*、*Finite time blowup for the Euler equation* |
| 形式化环境 | Lean **4.34.0-rc2** + Mathlib + Lake；并提供 **Comparator 挑战**（`ComparatorChallenges/NavierStokes.json`、`Euler.json`）供外部独立检查 |
| 模型 | 未发布的内部模型，"significantly more capable than GPT-6 Astra"，训练方式是 *"large-scale reinforcement learning on top of a previously pretrained model"* |

### 3.2 系统架构（OpenAI 自己的描述，逐句很关键）

- 这是一个"**coordinating agents**"系统，由内部模型驱动；
- 每个 agent 的工具：**读取缓存的互联网快照（cached version of the internet）**、**执行代码**；
- **agent 被划分为组，组内可以通信**；各组规模不同，攻 NS 的那一组规模约 10,000 并发；
- 早期 OpenAI 其实是在**同时试探 6 个未解千禧年问题**（含用更简单的问题"热身"），直到 9/1 听到"别处有进展"的传言，才把资源集中到 NS【报道·单一来源：Donga Science 转述，未见于 OpenAI 一手文本】；
- 攻主问题前，**先让 agent 打更简单的前置问题（Euler 方程）**，拿到"Euler 正则性反证"后再上 NS——这一步被 Buckmaster 的描述证实：*"the team first set the model on easier problems, including Euler"*；
- 另一个模型（Astra）专职做 **Lean 形式化与验证**（17 小时）；有报道称 Codex 承担"汇总思路并交叉分发"的中枢角色【报道·多方一致，但细节来自二手】。

**可迁移的两个结构选择**：
1. **"多组 × 组内通信 × 组间不通信"** 的分区式采样——天然产生多样性，又避免全局串扰；
2. **先易后难的课程式推进**：用简化问题（Euler）把搜索空间压到可解，再把结论作为上下文迁移到主问题。

### 3.3 结果到底覆盖了什么（这是最容易被标题误导的地方）

以 OpenAI 自己仓库 README 的**逐字表述**为准【一手·官方】：

- **Navier–Stokes（对每个正粘度）**，两条结论：
  - **全空间 ℝ³**：存在**光滑初始数据 + 光滑外力**，使得不存在动能一致有界的整体光滑解；
  - **环面 ℝ³/ℤ³**：存在光滑周期初始数据 + 外力，使得不存在整体光滑解。
  - README 明确把它们对应到 Clay 官方题面（Fefferman 撰写）里的选项 **(C)** 与 **(D)**。
- **Euler（无外力）**：构造出 ℝ³ 上光滑、紧支、无散的初始速度场，使**无外力**不可压 Euler 方程在有限时间出现奇点（C¹ 范数无界、涡量 L∞ 范数的时间积分发散）。

因此：
- 这是 **Clay 题面里 (C)/(D) 两条路线上的结果**（允许光滑外力），**不是**"无外力版本 NS 必然光滑/必然爆破"的答案；The Batch 的表述是"Clay 的官方题面允许这个结果"，而 Forkast 等媒体直接说"解错了问题"——**两种表述都在流通，引用时务必写清是哪一条**【报道·存在分歧】；
- OpenAI 明确表示**不申领** 100 万美元奖金：*"Our goal in releasing this result is to report on the substantial progress of our AI models… We do not intend to claim the Millennium Prize for this result."*
- Clay 方面的门槛：**公开发表 + 两年等待期 + 数学界普遍接受与专家复核**；截至 2026-09-19，**尚无独立复核完成**。

### 3.4 与"抢发"争议的接口（必须按双方说法并列）

**【Buckmaster 声明原文】** <https://cims.nyu.edu/~tristanb/statement.pdf>（9/7 深夜发布）
- 他与 Anthropic 研究员 Levent Alpöge 是**私人合作**（不属于任何机构），一年来用 **Claude、Codex（GPT-5.6 Sol）、以及后来的 Astra**（Astra 只用于写稿与审计）推进；

- *"I can say the first LLM generated proof Levent sent me was the most horrendous I have ever read."*
- 对那篇 Euler 的 write-up 的评价：*"can only be described as AI slop. I am sorry for this."*

- 他称对方提出两个方案（他们先发 Euler、OpenAI 次日发 NS；或他单独署名写 NS 的论文、不带 Alpöge），他拒绝；并称听到 "Why would you ruin your career?" 与 "If you don't want me to be nice, then I don't have to be nice."
- 他明确声明：*"I have not seen OpenAI's proof. I do not know what their model did, or how. I do not know whether our data was used. I am not accusing anyone of anything."*
- 他称这是 **"a Deep Blue–Kasparov moment"**，并认为 *"the results are not the important thing. Rather the important thing is instead the significance that a mathematician and an LLM model can now do all this work in a month."*

**【OpenAI 的说法】**【报道·多方一致】
- 承认**是因为听到"别处解决了千禧年问题"的传言才启动**这轮工作，且事后确认传言与他们两人有关；

**【第三方技术观点】**

- Tao（9/9）：把 Alpöge–Buckmaster 的工作称为 "astonishing achievement"；同时写下那段被广泛引用的话——**好问题比好答案更稀缺**，*"even the rumor of someone working on a problem can trigger a massive amount of AI-powered effort to flatten it before the original research project has time to reach its full potential"*，并警告这会**逆转数百年的开放科学传统**。

## 4. 案例 D（对照组）：把 LLM 当"推进器"而不是"解题器"

Buckmaster–Alpöge 这条线展示了一种和上面两种都不同的用法，而且更接近多数研究者现在能复制的形态：

- **人类提供数学纲领**（Córdoba–Martínez-Zoroa 的 forced blowup 思路），**LLM 负责把纲领"推过技术关口"**：从"粗糙外力"推到"光滑外力"，从 Euler 推到不可压 Euler；
- **验收仍然是 Lean**：先有 Lean 证书，再补人话论文（8/22 验证，9/7 公开）；
- **代价是"可读性崩塌"**：证明形式正确但人类读不懂（"the most horrendous I have ever read"、被作者自己称为 "AI slop"）。Buckmaster 因此宁愿**先给数学论证、后给形式证书**，这恰好与 Anthropic 那种"先给证书"的思路相反。

**这说明**：形式验证解决的是"对不对"，没解决"为什么"和"能不能被理解/传播"。The Batch 的总结很到位：*"a formally correct proof doesn't tell you why it works, whether the problem statement is correct, or what meanings can be drawn from it. While automated verification has become relatively inexpensive, human-readable understanding remains costly."*

### 4.5 信任模型的两个"反例"（2026 年必须知道的背景）

**反例一：Lean 内核 bug 让"假证明"骗过了 Lean 和独立内核（2026 年 7 月）**

- 2026-07-25，形式验证专家 Ramana Kumar 在 GitHub 发布 `xrchz/CollatzLean`，声称"在 AI 协助下推翻了 Collatz 猜想"。该项目**没有用 `sorry`、没有加公理、通过了 Lean 内核**，甚至还**通过了独立的 Rust 内核 Nanoda**；
- 但它无效：Lean 内核在处理 **nested inductive types** 时，"phantom type parameters" 被漏掉，使得类型不匹配的构造绕过检查，于是可以证明 `False`（从而证明任何命题）。修复于 Lean **4.32.2**（2026-07-28）；Leonardo de Moura 发布了 postmortem（bug #14576）：<https://leodemoura.github.io/blog/2026-8-1-postmortem-for-kernel-soundness-bug-14576/>；
- 更麻烦的是：**当时那个较老版本的 Nanoda 另有一个不相关的 bug**，恰好看不见这种构造——**两个独立实现的、互不相关的 bug 同时被利用**，于是"双内核交叉验证"这次也没兜住；
- 附带事实：Lean FRO 随后增加了预防性测试，OpenAI 的 Daniel Selsam 用"面向安全的 AI"协助调查，又找出若干实现错误并修复。

**这对判读 9 月两项成果的意义**：

| 项目 | 钉住的 Lean 版本 | 意义 |
|---|---|---|
| Anthropic FLT | **Lean 4.33.1**（README 明确写 "which includes the 2026 kernel soundness fixes"） | 已经含 7 月内核修复 |
| OpenAI NS/Euler | **Lean 4.34.0-rc2** | 在 4.33.1 之后，另含 Trail of Bits 报告的 `String.Pos.Raw.extract` 修复线（4.34.0-rc1） |

**反例二：`native_decide` 把编译器放进可信边界**（见 §1.3 Trail of Bits 那段）。两个反例的共同教训是：**"编译通过"不是自证；可信边界必须被显式检查（公理白名单 + 语句对齐 + 版本对齐 + 独立内核）。** 这也是为什么 Anthropic 把"公理必须是那三条"写成**构建期断言**、OpenAI 给出 Comparator 挑战脚本——这两件事在 2026 年属于**必备动作**，而不是加分项。

## 5. 横向拆解：四种"AI 用法"的构件表

| 构件 | Anthropic FLT | Anthropic RH | OpenAI NS | Buckmaster–Alpöge |
|---|---|---|---|---|
| 智能体载体 | Claude Code 多 agent harness | Claude Code（两 session） | 自研 coordinating agents | 人机对话式（Claude/Codex/Astra） |
| 任务分解 | **Prove2Me 的定理 DAG** | 子 agent 分工（想法/验证/写作） | 组内通信 + 先易后难课程 | 人类给纲领，模型补技术步骤 |
| 并行度 | 几十个 agent | ~60 子 agent | **~10,000 并发** | 低（人机协作） |
| 反馈信号 | Lean 编译器（强、自动） | 数值检验 + 互审 + Lean | Lean（形式化阶段）+ 组内互评 | Lean |
| 防幻觉手段 | 编译器 + comparator + 公理审计 | 反例搜索、arXiv 查重、独立重证 | 形式化 + 多组并行（**弱**：无独立复核） | 人类的数学判断 |
| 人类角色 | 只给高层方向 | 只给"鼓励" | 选题、切分问题、事后争议 | 提供核心想法、判断路线 |
| 耗时/成本 | 11 天 / 60 亿 token | 1.5 天 / 3100 万 token | 88+17 小时 / ~3000 亿 token / 数百万美元 | 一年（人时为主） |

**由此可以提炼出 2026 年"AI 做数学"的三条工程定律**：

1. **验收器的强度决定了自治程度。** Lean（+comparator+公理审计）是唯一可以"无人值守跑 11 天"的验收器；OpenAI 这条线之所以必须靠"上万 agent + 巨额算力 + 事后再吵优先权"，恰恰因为**在"发现新证明"的早期阶段没有廉价验收器**。
2. **DAG / 子目标管理是长周期任务的生命线。** Anthropic 明说第一次尝试失败的原因是"agent 丢失项目状态、不再有效协作"；换到 Prove2Me 的"定理语句 DAG + 语句与证明分文件 + 自然语言描述"后才成功。**这不是模型能力问题，是工程问题。**
3. **"先易后难 + 组内通信/组间隔离"是低成本换搜索多样性的手段。** OpenAI 先打 Euler 再打 NS；RH 案例里 60 个子 agent 里 30 个注定失败——**失败分支的预算必须被显式设计进去**。

## 6. 人类现在在做什么（2026 版分工）

- **选题与路线判断**：Córdoba–Martínez-Zoroa 的 forced-blowup 纲领是人类的；Tao 担心的正是这一环的稀缺化。
- **把问题切分/降维**：先 Euler、后 NS；先证小引理、再用 DAG 级联（AI 能做，但切分方式由人设定或人审）。
- **写验收标准**：Lean 语句与 Mathlib 语句对齐（comparator）、公理白名单——这是**人类必须负责**的部分。
- **把形式证明翻译回理解**：Buckmaster 花了几周把 LLM 的证明"读成人类能懂的"，并称之为最花时间的部分。
- **仲裁与规范**：署名、优先权、数据来源、是否公开——9 月这场争议说明，**制度问题已经开始成为瓶颈**。

### 6.5 数学界的正式表态：25 位菲尔兹奖得主宣言（2026-09-11）

要判断这些"用法"是否可持续，必须看数学界自己的反应。9 月 11 日，**25 位菲尔兹奖得主**（Artur Avila、Manjul Bhargava、Caucher Birkar、Pierre Deligne、Martin Hairer、June Huh、James Maynard、Peter Scholze、Terence Tao、Maryna Viazovska、Cédric Villani、Efim Zelmanov 等）联署发表宣言，Tao 在自己的博客给出全文：<https://terrytao.wordpress.com/2026/09/11/a-severe-misalignment-of-ai-in-mathematics/>

核心段落（逐字）：

> *"the push by AI companies to solve mathematical problems as a benchmark is detrimental to the science of mathematics, and to the mathematical community. **The goals of the AI companies and the goals of the mathematical community are severely misaligned.**"*
>
> *"Often these solutions are announced in a rush, leaving no time for a proper writeup, the isolation of new methods and ideas, and citing relevant previous work of others. As in all creative professions, this raises **severe attribution and plagiarism questions**."*
>
> *"the mass production at faster and faster pace of 'true/false' statements could **destroy fertile ground** instead of breathing life into new ideas."*

**为什么这与"AI 怎么用"直接相关**：它给出的是一条**评价标准**——如果 AI 的用法只产出"真/假"结论，而不产出"方法被隔离出来、被社区理解、被写进教科书"的中间过程，那么它在数学界的价值判定会很低。对照本文四个案例：
- Anthropic FLT 恰好**符合**该标准（不产生新数学、但把验证做成公共品、并由 Buzzard 背书）；
- OpenAI NS 恰好**触碰**该标准列出的每一条（抢发、无暇写清、方法未隔离、致谢与前人工作归位不足）；
- Buckmaster–Alpöge 那条线则同时体现了宣言的另一面——他们最花时间的部分恰恰是"把 LLM 的证明读成人类能懂的东西"。

## 7. 可信度分级：哪些是"已确证"，哪些只是"宣称"

**已经机器确证（可复现）**
- Claude 的 FLT 形式化：Lean 通过、仅三条标准公理、comparator 对齐 Mathlib 语句、代码公开、Buzzard 复核。→ **这是 2026 年最干净的一次"AI + 形式化"成果**。
- Anthropic 的 RH 结果：有论文、有 Lean 形式化、经 comparator、两位内部数学家与 Conrey/Goldston 过目。→ 数学内容本身**不是**黎曼猜想的证明，Anthropic 自己也这么说。

**已形式化、证书已公开，但未经独立复核**
- OpenAI 的 NS 结果：166 页论文 + Lean 证书 + **Comparator 挑战**均已公开（<https://github.com/openai/NavierStokesAndEuler>），并且其 NS 题面形式化是**改编自 Google DeepMind "Formal Conjectures" 项目**对 Clay 题面的 Lean 形式化（README 致谢）——这大幅降低了"语句漂移"的风险。但：
  - **截止 2026-09-19 无独立复核完成**（媒体曾出现"未公开、无法审计"的说法，与仓库实际状态不符，应以仓库为准）；
  - 结果只覆盖 Clay 题面 **(C)/(D)**；
  - 论文未见 arXiv/期刊投稿记录，未经同行评审。

**存疑/未决**
- OpenAI 的算力与消息口径需要按"单项 vs 全部"读：**NS 单项 270 万消息 / ~1300 亿 token；本次所有问题合计 490 万消息 / ~3000 亿 token**（两个数字都被当成"NS 的数字"传播过）；另外 agent 数也有"近 100 个"与"1000 个"两种说法（分别对应 Euler 阶段与另一处转述）——**引用时必须写明口径与来源**。
- Codex 会话数据是否参与了训练：OpenAI 先称"无法排除"，后称"不可能影响"，并**未回应更早的记录**。
- 成本估算（200 万 ~ 2250 万美元；另有 ~1500 万美元一说）全部是**外部按标价推算**，非官方披露。
- OpenAI 的 Lean 证书**是否做过公理审计（`#print axioms`）**、以及在多少个独立内核上重放过，官方材料未见说明；其 Comparator 挑战脚本已公开，**任何人都可以自己去跑**——这是目前最值得做的独立复核动作。

**已验证 ≠ 已解决**
- 形式化只保证"命题在该形式系统内为真"；**命题是否就是你想证的那个**（statement alignment）、**以及证明是否有价值/可理解**（novelty & readability），都不在形式化的射程内。
- 量化证据：Lean-as-judge 类审计显示，**只有约 43% 被"证明"的形式语句忠实于原本想表达的数学**（Bourigault et al., 2026，转引自 Prove2Me 论文）。因此判读这类成果时，**"语句对齐 + 公理审计"比"证明通过"更值得看**。

## 8. 对 AIMO 这类"竞赛型 AI 数学"的启示

对照本目录 `AIMO3-方案综述.md` 的结论（模型能力 > 推理侧技巧、harness 是公共品、单次分数噪声大），可以看到一条清晰的**能力-资源分界线**：

1. **量级差不是技巧差**：AIMO3 是"单卡 H100 / 5 小时 / 断网 / 50 道题"，前沿实验室是"上万 agent / 88 小时 / 数千亿 token / 数百万美元"。**在 5 小时单卡预算里复制 OpenAI 那种 swarm，物理上不成立。**
2. **能迁移的只有三样**：
   - **子目标 DAG 管理**（把一道题拆成"定义 → 小引理 → 主命题"，并在失败后可恢复）——这与 Prove2Me 的思路同源，但需要题目结构足够复杂才划算；
   - **验证者子 agent 而不是多数投票**：RH 案例里 13/60 的子 agent 专职当 validator，且互相 referee。这与 AIMO3 里"verifier 基本负收益"的结论并不矛盾——**AIMO3 的答案空间只需一次格式/范围校验（0~99999 的整数），没有可供 verifier 发挥的结构**；
   - **机器可判定的验收器 = 熵加权自洽的加强版**：AIMO3 里"整数答案 + 格式校验"就是那个廉价验收器，因此方案的最优形态退化成"采样 + 聚合"；**有 Lean 的地方才会长出多智能体工程**。
3. **最值得注意的一条反直觉经验**：Anthropic 用 11 天 × 60 亿 token 换来的是**"验证"**而非"发现"；而 3000 亿 token 的 OpenAI 版本换来的是一次**范围有争议的发现**。**当验收器强时，算力换确定性；当验收器弱时，算力换的是"路线命中率"，而且必然伴随优先权与可复现性争议。**

## 10. 如果只记几条

1. **Anthropic 的 2026 数学成果 = "用 AI 做验证"**：11 天、60 亿 token、1300 万行 Lean、只依赖三条标准公理。它的成功要素不是模型有多强，而是**换上了 Prove2Me 这种为多 agent 设计的协作/DAG 基础设施**。
2. **OpenAI 的 2026 数学成果 = "用算力做搜索"**：~10,000 并发 agent × 88 小时（+17 小时 Lean）、约 3000 亿 token、数百万美元，先打 Euler 再打 NS。它证明了**大规模 test-time compute 可以推进未解问题**，但也暴露了**没有强验收器时的优先权、透明度与可复现性问题**。
3. **两者共同的新事实**：形式化（Lean）已经从"数学家的爱好"变成**AI 数学流水线的验收层**——它把"对不对"变成机器可判定，于是"AI 能不能被信任"这个问题，第一次有了工程化的答案（comparator + 公理审计 + 独立复核）。
4. **但这个验收层本身也有脆弱的时刻**：2026 年 7 月，"AI 反证 Collatz"同时骗过了 Lean 内核和独立内核 Nanoda （两个无关 bug 被同时利用），修复于 Lean 4.32.2；因此 9 月两项成果都钉住了带修复的版本（4.33.1 / 4.34.0-rc2）。**正确读法是：不要看"是否通过 Lean"，要看"公理白名单 + 语句对齐 + 内核版本 + 是否有独立重放"。**
5. **数学界的判断标准已经明确写出**：9 月 11 日 25 位菲尔兹奖得主发表宣言，认为"把解数学题当作 benchmark 的 AI 竞赛"与数学共同体目标"严重错位"，并点名"抢发式公布会带来严重的署名与抄袭问题"。评价 2026 年任何一项 AI 数学成果时，**这份宣言就是那份评价标准**。
